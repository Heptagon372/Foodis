## 1. 1만 개 최적화 — 무엇이 느렸고 어떻게 줄였나

### 1.1 화면 (프로덕션 빌드, 같은 페이지 두 번째 요청)

| 화면 | 전 | 후 | 바꾼 것 |
|---|---|---|---|
| 홈 `/` | 8.0MB · 4.4초 | **1.08MB · 94ms** | 1만 개 전부 → 나라별 대표 8개(≈1,300). 예전 조건 "소개가 있는 음식"을 1만 개가 모두 통과했다 |
| 맛집 `/eats` | 3.0MB · 4.3초 | **0.79MB · 57ms** | 고를 수 있는 음식: 나라별 대표 20개 (한국에서 파는 곳을 찾는 화면) |
| My Table `/passport/table` | 3.96MB · 3.2초 | **54KB · 11ms** | 1만 개 조회표를 통째로 → 내 기록에 있는 음식만 `/api/foods/table` 로 |
| 지도 · 라디오 · 빈 나라 | 3.2~3.5초 | 12~115ms | 아래 목록 캐시 |
| 전체 p95 | 4,254ms | **404ms** | |

**목록 캐시** (`lib/content/supabase-source.ts`): `listFoods()` 가 요청마다 1만 행을 11쪽으로 **차례로** 받고 있었다(force-dynamic 화면마다).
→ 서버 프로세스 하나에 하나, 5분 동안 그대로 쓰고 지나면 옛 목록으로 답하면서 뒤에서 새로 받는다(stale-while-revalidate). 쪽은 동시에 받는다. 상세 화면은 캐시하지 않는다(어드민 수정이 바로 보이게).

### 1.2 푸디

| 무엇 | 값 | 장치 |
|---|---|---|
| 검색 색인 처음 받기 | 3.5초 → **서버 시작 때 미리** | `instrumentation.ts` (node 전용 import) |
| 질문 하나 처리 (LLM 제외) | p50 16ms · p95 23ms | 1만 개 전부에 점수식 — 역색인으로 비슷한 음식 후보만 |
| 같은 나라·같은 이름 중복 17쌍 | 검색에서 하나로 | 대표성 → 사진 → 재료 수로 남길 쪽. DB 는 그대로 |
| 의미 검색 RPC | v1: 계산 점수로 정렬 → HNSW 를 못 타고 전체 스캔 (846개일 때 110~550ms) | `0012_match_foods_v2.sql`: 거리순 + LIMIT → 인덱스. 앱은 v2 가 있으면 쓰고 없으면 v1 |
| 임베딩 일부만 있을 때 | 임베딩 있는 8%만 의미 점수를 받아 순위가 쏠림 | 공개 음식의 **95% 이상**에 임베딩이 있을 때만 의미 신호를 켠다 |

### 1.3 비용·한도 — 지금 키는 **Gemini 무료 등급**

| 한도 | 값 (2026-10-07 실측 429 응답) | 영향 |
|---|---|---|
| 임베딩 분당 | 100건 (문서 하나가 1건) | 일괄 생성은 분당 80으로 (20은 사용자 질문 몫) |
| 임베딩 하루 | **1,000건** | 1만 개를 무료로 채우면 약 10일. 사용자 질문 임베딩도 같은 한도를 쓴다 |
| LLM | 무료 등급 분당 한도 | 라이브 30문항 연속에서 7건이 템플릿 답으로 (안전하게 떨어짐) |

→ **경진대회 데모 전에 Google AI Studio 에서 결제를 켜는 것을 권한다.** 1만 개 임베딩 약 $0.7, 질문 1,000개 약 $1.6/일 (09 문서 v2). 결제를 켠 뒤 `EMBED_RPM=3000 pnpm embed:foods` 면 몇 분.
무료로 갈 경우: 매일 `pnpm embed:foods -- --limit 900` (만든 것은 저장되고 다음 날 이어진다). 그동안 푸디는 의미 신호 없이 규칙·점수식으로 답한다(§0 오프라인 지표가 그 수준).
