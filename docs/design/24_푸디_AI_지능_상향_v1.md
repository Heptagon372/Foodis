## 2. 설계 원칙

불변 (04 문서 §5 · 19 문서):
1. **사실은 DB** — 새로 추가되는 LLM 호출(재작성·계획·재랭킹·검증)은 전부 "DB 가 준 것 안에서 고르거나 지우는" 일만 한다. 새 사실을 만들 수 있는 호출은 없다.
2. **어느 단계가 죽어도 카드 있는 답** — 새 단계는 전부 `try → 실패 시 v2 경로` 로 감싼다. v3 는 v2 위에 얹는 선택 층이다.
3. **예산** — 하루 `DAILY_BUDGET_USD` 안에서. 단순 질문(한 턴·단일 의도·검색 확실)은 **추가 호출 0** 이어야 한다.

신설:
4. **규칙이 먼저, LLM 은 규칙이 모를 때만** — 지시어 해소·복합 질문 감지·검색 평가는 규칙(정규식·점수 임계)이 1차, LLM 은 2차. `intent.ts` 가 이미 이렇게 되어 있다 (절반 이상 LLM 생략).
5. **모든 새 층은 오프라인 테스트 가능** — 가짜 LLM(`orchestrator.test.ts` 패턴)과 1만 개 정리본(`eval/import-repo.ts`)으로 네트워크 없이 검증. 라이브는 `eval:live` 에 문항만 보탠다.
6. **측정 없이 켜지 않는다** — 각 장치는 지표(§7)와 끄는 스위치(환경변수)를 가진다.

## 3. 아키텍처 v3

```
사용자 발화 + 최근 턴 3개(클라이언트 turns)
   │
   ▼
[K] 사회적 발화? (발화 전체가 인사·감사·작별·안부·기분) → 페르소나 템플릿 답 (LLM·검색 0) → 끝   ★ 구현됨
   │ 아니면
   ▼
[A] 대화 상태 추적 ─ 규칙 병합("더 매운", "거기 말고", "그거") ─ 못 풀면 LLM 재작성(fast) → 완전한 질문 1문장
   │
   ▼
[B] 복합 감지(규칙: 접속·둘 이상 의도 신호) ─ 아니면 건너뜀 ─ 맞으면 계획(fast) → 단계 ≤3
   │  (각 단계는 아래를 독립 실행)
   ▼
[J] 의미 캐시 (질의 임베딩 코사인 ≥ 0.95 ∧ QuerySpec 해시 일치 ∧ 프로필 구간 일치) → 적중이면 끝
   │
   ▼
의도·슬롯 (v2 그대로)  ∥  질의 임베딩  ∥  HyDE 가설 문서 임베딩(애매할 때만)
   │
   ▼
[C] 하이브리드 검색: 하드 필터 → {BM25(이름·소개·재료·이야기) , 벡터 120 , 슬롯 충족} → RRF 융합 → 7신호 점수(v2) → 계단식 → MMR 10
   │
   ▼
[D] 검색 평가기: 확실(top 점수·여유·충족) / 애매 / 실패
   │        애매 → [E] LLM 목록 재정렬(10 → 5) + HyDE 재검색      실패 → 정직한 "못 찾았어요" + DB 대안 (템플릿)
   ▼
생성 (v2 프롬프트, 후보 5)  →  규칙 검증 (v2)  →  [F] 장문이면 주장 대조(지우기·1회 재생성)
   │
   ▼
[G] 밴딧이 고른 '추천 전략'(가중치 세트)이 위 점수에 쓰였음을 로그에 남김 (propensity) → 카드 탭·좋아요가 보상
   │
   ▼
기록: conversations(+session_id, turn_no, rewritten_text, plan, verdict, strategy, propensity) → [I] 심사·[E] 학습·[G] 정책 평가의 재료
```

단순 질문의 경로는 v2 와 같다: A(규칙만) → B(건너뜀) → J(실패) → 의도 ∥ 임베딩 → C(RRF 는 CPU) → D(확실) → 생성 → 검증. **LLM 호출 수 2 (의도는 규칙이 절반 생략) 그대로.**

## 4. 설계도 10장

### A. 대화 상태 추적 + 질의 재작성 — "그거 말고 더 매운 거"

**논문** — Conversational Query Rewriting: Elgohary et al., *Can You Unpack That? Learning to Rewrite Questions-in-Context* (EMNLP 2019, CANARD) · Yu et al., *Few-Shot Generative Conversational Query Rewriting* (SIGIR 2020). 대화형 검색에서 **문맥 의존 질문을 독립 질문으로 고쳐 쓴 뒤 기존 검색기를 그대로 쓰는 것**이 검색기 자체를 대화형으로 바꾸는 것보다 싸고 강하다는 결과. 대화 상태 추적(DST)은 Hudeček & Dušek, *Are LLMs All You Need for Task-Oriented Dialogue?* (SIGDIAL 2023) — 슬롯 상태를 LLM 이 JSON 으로 갱신하는 방식.

**푸디에 어떻게**
- 클라이언트가 이미 가진 `turns` 중 **최근 3턴**을 보낸다: `history: [{ role: "user"|"foodi", text, intent?, cards?: slug[] }]` (`AskRequest` 확장, 최대 3·각 300자).
- 서버는 **대화 상태** `DialogState` 를 이전 턴 응답에서 복원한다 (저장 없음 — 클라이언트가 보내는 history 에서 매번 재구성, 로그인·게스트 동일):

```ts
type DialogState = {
  focusFood: string | null;        // 마지막 카드 1장 또는 explain 대상 ("그거")
  lastCards: string[];             // "그거 말고" 의 제외 대상
  countryCode: string | null; continent: string | null;   // "거기"
  spec: QuerySpec;                 // 누적 조건 ("더 매운" = spec.tags + spicy, 나머지 유지)
  needDiet: DietKey[];
  lastIntent: Intent | null;
};
```
- **규칙 병합 (1차, 비용 0)** — `lib/foodi/dialog/state.ts`
  - 지시어: `그거|그 음식|이거|저거|아까 (그|거)` → `focusFood` / `거기|그 나라|그쪽` → `countryCode`
  - 비교급·증감: `더 (매운|달콤한|…)` → `spec.tags += tag`, 기존 조건 유지 / `덜 매운|안 매운` → `notTags`
  - 배제: `(그거|거기) 말고|빼고|다른 (거|나라)` → `exclude += lastCards` 또는 `countryCode = null + notCountries`
  - 생략 질문: 음식 이름·나라·조건이 하나도 없고 의도 신호만 있으면("역사는?", "비건이야?") → `focusFood` 를 대상으로
  - 결과를 **완전한 문장**으로 다시 조립해 v2 파이프라인에 넣는다 (`rewritten_text`). 조립 틀: `[나라] [누적 조건] [범주] [의도어]`.
- **LLM 재작성 (2차)** — 규칙이 지시어를 발견했지만 가리키는 대상을 못 정했을 때만 (`fast` 티어, 구조화 출력 `{ standalone: string, uses_history: boolean }`). 프롬프트 `prompts/rewrite.v1.ts`: "history 와 question 을 보고, history 없이도 뜻이 같은 한 문장으로. 새 조건·음식 이름을 보태지 않는다." 재작성 결과도 **이름 인식기(`names.ts`)로 검증**: history 와 질문에 없는 DB 음식 이름이 나오면 버리고 규칙 결과를 쓴다.
- **캐시 키**: `rewritten_text` 로 계산 (history 가 있는 턴은 지금처럼 캐시 안 함 — `seen_food_ids` 조건과 같다).

**비용·지연** — 규칙 경로 0. LLM 재작성은 지시어가 있는 턴에만 (로그 추정 10~15%), 입력 ≈ 400토큰 → **$0.0001 · 0.3~0.6초**.
**지표** — 다중 턴 세트 20대화·60턴 (§I) 지시어 해소 정확도 ≥ 90%, 1턴 질문 회귀 0.
**위험** — 재작성이 뜻을 바꾼다 → 이름 검증 + `uses_history=false` 면 원문 사용. history 는 **데이터로만** 취급 (프롬프트 §10 규칙 그대로, 주입 차단).

### B. 계획-실행 — 복합 질문

**논문** — Yao et al., *ReAct: Synergizing Reasoning and Acting in Language Models* (ICLR 2023) · Wang et al., *Plan-and-Solve Prompting* (ACL 2023). 복잡한 요청을 **먼저 단계로 쪼개고(계획) 각 단계를 도구(여기선 v2 파이프라인)로 실행한 뒤 합치는** 구조. 푸디는 도구가 하나(음식 검색·설명)라 ReAct 의 "생각-행동 반복"까지는 필요 없고, Plan-and-Execute 의 **고정 계획 ≤ 3단계**면 충분하다.

**푸디에 어떻게**
- **감지(규칙)** — `하고|그리고|도 |또|랑 ` 접속 + `ruleClassify` 가 **의도 신호를 2종 이상** 찾을 때 (예: 추천어 + `역사|유래|이야기`). 아니면 계획 단계 없음.
- **계획(fast LLM, 구조화)** — `{ steps: [{ intent, text, depends_on_previous: boolean }] }` 최대 3. `text` 는 그 단계만의 완전한 질문. 검증: 각 `intent` 는 `INTENTS` 안, `text` 에 질문에 없는 DB 음식 이름이 없을 것.
- **실행** — 각 단계는 `ask()` 의 내부 함수 `askOnce()` (v2 본체를 분리) 로 **순서대로**. `depends_on_previous` 면 앞 단계의 카드 1장을 `context_food_id` 로 넘긴다 ("비건 디저트 추천하고 **그** 역사도").
- **합성(LLM 없이)** — speech = 단계별 speech 를 이어 붙이되 총 3~4문장(각 단계 첫 2문장), cards = 단계 카드 합집합 ≤ 3, follow_ups = 마지막 단계 것. 각 단계의 `validated` 가 전부 참일 때만 합성 답을 캐시.
- **예산** — 단계 수만큼 LLM 호출이 늘므로 복합 질문은 `overBudget` 이면 첫 단계만.

**비용·지연** — 복합 질문에만: 계획 1회(fast, $0.0001) + 단계 수 × v2 비용. 지연은 단계 직렬 (2단계 ≈ 2×). 음성 UX 를 위해 **첫 단계 speech 를 먼저 스트리밍**하고 두 번째를 이어 붙이는 것은 P3.
**지표** — 복합 질문 세트 30문항: 두 요구 모두 충족 ≥ 85%, 단일 질문이 복합으로 오인되는 비율 ≤ 2%.
**위험** — 계획이 질문에 없는 요구를 보탠다 → 단계 `text` 의 어휘가 원문·history 어휘 안에 있는지 검사(이름·나라·식이·재료).

### C. 하이브리드 검색 — BM25 + 임베딩 + HyDE, RRF 융합

**논문** — Robertson & Zaragoza, *The Probabilistic Relevance Framework: BM25 and Beyond* (FnTIR 2009) · Cormack, Clarke & Büttcher, *Reciprocal Rank Fusion Outperforms Condorcet and Individual Rank Learning Methods* (SIGIR 2009) · Gao et al., *Precise Zero-Shot Dense Retrieval without Relevance Labels* (HyDE, ACL 2023). 어휘 검색과 의미 검색은 서로 다른 것을 놓치고, **순위만 가지고 합치는 RRF** 가 점수 보정 없이도 둘보다 낫다. HyDE 는 질의 대신 **"있을 법한 문서"를 LLM 이 쓰게 한 뒤 그 임베딩으로 검색**해 짧고 모호한 질의("해장 되는 거", "할머니 손맛 같은")의 벡터 검색을 크게 올린다.

**푸디에 어떻게**
- **BM25 (메모리)** — `lib/foodi/lexical.ts`. 1만 개 × 필드(이름 3배 · 소개 · 재료 · 문화 이야기 앞 300자)를 서버 색인(`food-index.ts`)에 같이 올린다. 토큰: 한국어는 2-gram + 공백 단위 어절 (형태소 분석기 없이), 영어는 소문자 어절. 문서 ≈ 10k × 120 토큰 → 역색인 수 MB, 질의당 < 5ms.

  $$\mathrm{BM25}(q,d)=\sum_{t\in q}\mathrm{idf}(t)\cdot\frac{f(t,d)\,(k_1+1)}{f(t,d)+k_1\!\left(1-b+b\,\frac{|d|}{\overline{|d|}}\right)},\quad k_1=1.2,\ b=0.75$$

- **RRF 융합** — `lib/foodi/fuse.ts`. 세 순위 목록(BM25 상위 120 · 벡터 상위 120 · 슬롯 충족도 상위 120)을

  $$\mathrm{RRF}(d)=\sum_{r\in R}\frac{1}{k+\mathrm{rank}_r(d)},\quad k=60$$

  로 합쳐 **후보 풀 200** 을 만든다. 그다음 v2 의 7신호 점수(`scoreFoods`)·계단식·MMR 은 그대로 — 다만 `s_sem` 자리에 "RRF 정규화 값"을 하나 더 신호로 넣는다 (`fuse` 가중치 0.15, 나머지는 비례 축소). 즉 **RRF 는 '누구를 후보로 볼지'를, 7신호는 '그중 누가 먼저인지'를** 정한다.
- **HyDE** — 검색 평가기(D)가 "애매"라고 할 때만: fast LLM 에 "이 질문에 맞는 음식 소개글 2문장을 **음식 이름 없이** 써라" → 임베딩 → 질의 임베딩과 평균 → 벡터 재검색. 이름을 금지하는 이유: 가설 문서는 **검색 열쇠일 뿐 후보가 아니다** (사실 규칙 1). 결과는 후보 풀에 합치고 다시 RRF.
- **임베딩 100% 전제** — 의미 신호의 95% 규칙은 유지. 임베딩이 꺼진 동안은 BM25 + 슬롯 두 목록만 RRF. (Gemini 결제 후 `EMBED_RPM=3000 pnpm embed:foods`, 약 $0.7.)

**비용·지연** — BM25·RRF 는 CPU (p50 +3~5ms). HyDE 는 애매할 때만 fast 1회 + 임베딩 1회 ≈ $0.0001 · 0.5초.
**지표** — `eval:retrieval` 에 ⑧ **뉘앙스 세트** 추가: 소개글에만 단서가 있는 질문 40개("해장", "명절", "길거리", "아침", "축제") 의 상위 5 적중률 — BM25 만으로 ≥ 60%, 임베딩 켜지면 ≥ 80%. ④ 조건 충족률 94.4% 유지 이상.
**위험** — BM25 가 흔한 말("음식", "요리")에 끌린다 → 불용어 + idf 하한. 이름 2-gram 이 "아시아"→"아시" 오인 → 이름 필드는 `names.ts` 인식기가 찾은 구간만 쓰고 BM25 는 소개·재료·이야기 필드에만.

### D. 교정형 RAG — 검색을 먼저 의심한다

**논문** — Yan et al., *Corrective Retrieval Augmented Generation* (CRAG, 2024) · Asai et al., *Self-RAG: Learning to Retrieve, Generate, and Critique through Self-Reflection* (ICLR 2024). 검색 결과를 **평가기가 "맞음 / 애매 / 틀림"으로 판정**하고 애매하면 검색을 확장·정제, 틀리면 다른 길로 간다. Self-RAG 는 생성 중 "검색이 필요한가 · 근거가 뒷받침하나 · 답이 쓸 만한가"를 스스로 판정하는 토큰을 학습한다 — 푸디는 학습 대신 **규칙 평가기 + 소형 LLM 판정**으로 같은 구조를 만든다.

**푸디에 어떻게** — `lib/foodi/judge/retrieval.ts`
- 입력: `Scored[]` 상위 10 (점수 · `coverage.hard` · `parts`), `QuerySpec`, 의도.
- **규칙 판정 (비용 0)**:

| 판정 | 조건 | 다음 |
|---|---|---|
| 확실 | 1순위 `coverage.hard ≥ 0.99` ∧ (조건 없는 열린 질문이거나 1·2위 점수 차 ≥ 0.05) ∧ (의미 신호 켜졌으면 1순위 코사인 ≥ 0.45) | v2 그대로 생성 |
| 애매 | 조건이 있는데 `coverage.hard < 0.99` 인 후보만 있음 ∨ 상위 5 점수 차 < 0.02 ∨ 코사인 0.3~0.45 | **C-HyDE 재검색 + E 목록 재정렬** → 다시 판정 (1회) |
| 실패 | 모든 후보 `coverage.hard < 0.5` ∨ 하드 필터 뒤 후보 < 3 ∨ 코사인 < 0.3 (의미 켜짐) | 템플릿 "조건에 꼭 맞는 음식을 아직 못 찾았어요" + **가장 가까운 조건 완화 제안** ("'코코넛' 빼면 N개 있어요") |

- "실패"의 완화 제안은 `QuerySpec` 조건을 하나씩 빼 보며 후보 수를 세는 규칙 (CPU). LLM 이 아니라 **DB 가 말해 주는 정직한 포기**다.
- 판정·근거(`verdict`, `margin`, `top_cov`)를 `conversations` 에 기록 → §I 에서 판정 정확도를 심사.

**비용·지연** — 규칙은 0. 애매 판정 비율을 로그로 보고 임계를 조정 (목표 15% 이하).
**지표** — 심사(§I)에서 "애매·실패" 판정 턴의 사후 만족(카드 탭·좋아요)이 "확실" 턴 대비 어떤지, 그리고 **잘못된 확신** (확실 판정인데 심사 불합격) ≤ 3%.

### E. 재랭킹 — LLM 목록 재정렬 + 로그로 가중치 학습

**논문** — Sun et al., *Is ChatGPT Good at Search? Investigating Large Language Models as Re-Ranking Agents* (RankGPT, EMNLP 2023): 후보 10~20개를 **한 번에 보여주고 순위 목록을 받는 listwise 재랭킹**이 점수식보다 nDCG 가 높다. 학습 쪽은 Burges, *From RankNet to LambdaRank to LambdaMART* (MSR 2010) · Joachims et al., *Unbiased Learning-to-Rank with Biased Feedback* (WSDM 2017): 클릭은 **위치 편향**이 있으니 propensity 로 보정해 학습한다.

**푸디에 어떻게**
- **목록 재정렬 (애매할 때만, D 연동)** — `lib/foodi/rerank.ts`, 프롬프트 `prompts/rerank.v1.ts`. 후보 10개를 `[id] 이름 · 나라 · 맛 · 주재료 · 조리법 · 코스 · matched` 한 줄씩 → `{ order: id[] }`. 검증: 반환 id 는 입력 안, 누락은 뒤에 붙임. 결과 순위를 RRF 에 **네 번째 목록**으로 넣어 융합 (LLM 이 혼자 결정하지 않게). Liu et al., *Lost in the Middle* (TACL 2024) 대로 **최상위 후보를 목록 맨 앞과 맨 뒤에** 두지 않도록 10개로 제한하고 점수순 그대로.
- **가중치 학습 (오프라인 배치)** — `scripts/learn-weights.ts`. 점수식이 이미 선형 `S = Σ w_k s_k` 이므로 **RankNet 식 pairwise 로지스틱**으로 `w` 를 학습한다:
  - 표본: `conversations` 의 카드 노출 (후보 5 · `parts`) + `events`(0004) 의 카드 탭·좋아요·먹어봤어요 (24시간 내) → (클릭 음식 ≻ 노출만 된 음식) 쌍.
  - 위치 편향: 카드 위치별 클릭률의 역수로 쌍 가중 (Joachims 2017 의 IPS).
  - 손실 $\sum_{(i\succ j)} w_{ij}\log\left(1+e^{-(S_i-S_j)}\right)$, 의도 그룹(open·slotted·diet·story)별 `w`. 표본 < 300쌍이면 학습 안 함(현재 가중치 유지).
  - 결과는 `WEIGHTS` 를 덮어쓰지 않고 **`weights.learned.json` 으로 내보내 어드민에서 켜고 끈다** (A/B §I).
- LambdaMART(비선형)는 표본 1만 쌍 이상 쌓이면 P3.

**비용·지연** — 재정렬은 애매할 때만 fast 1회 (입력 ≈ 900토큰, $0.0002 · 0.6초). 학습은 배치(비용 0, LLM 없음).
**지표** — 재정렬 전후 nDCG@3 (심사 라벨 기준) +0.05 이상이어야 유지. 학습 가중치는 인터리빙(§I)에서 카드 탭 승률 > 50% 일 때만 기본으로.

### F. 검증 사슬 — 장문의 주장을 DB 문장과 대조

**논문** — Dhuliawala et al., *Chain-of-Verification Reduces Hallucination in Large Language Models* (CoVe, ACL 2024 Findings): 초안 → 초안의 주장마다 검증 질문 생성 → 근거만 보고 각각 답 → 모순 문장 수정. 충실성 판정은 Honovich et al., *TRUE: Re-evaluating Factual Consistency Evaluation* (NAACL 2022) 의 **NLI 식 "근거가 이 문장을 뒷받침하는가"** 와 Min et al., *FActScore* (EMNLP 2023) 의 **원자 주장 분해**를 쓴다.

**푸디에 어떻게** — `lib/foodi/verify.ts`, 프롬프트 `prompts/verify.v1.ts`
- 대상: `culture_story`(최대 400자) 와 `explain_food` 의 기원·역사 답. 추천 2~3문장은 v2 검증으로 충분.
- **경량 1회 호출판** (CoVe 의 4단계를 한 구조화 호출로): 입력 = 초안 speech + 그 음식의 DB 본문(summary · history · culture_story · origin_note · ingredients) → 출력 `{ claims: [{ text, supported: "yes"|"no"|"partial", evidence_span?: string }] }`. 규칙: 연도·인물·수치·재료·지명이 든 문장만 주장으로 본다 (감탄·제안 문장은 제외).
- 처리: `no` 가 하나라도 있으면 **그 문장을 지운 초안**을 만들어 다시 규칙 검증 → 2문장 이상 남으면 채택, 아니면 "지운 주장 목록"을 붙여 1회 재생성 (프롬프트에 "다음 내용은 말하지 마라"). 그래도 실패면 v2 템플릿(DB 문장 그대로).
- 판정 자체도 `conversations.verify` 에 기록 → 심사(§I)에서 판정기의 정밀도를 본다.

**비용·지연** — 장문 의도에만 fast 1회 (입력 ≈ 1,200토큰, $0.0002 · 0.7초). 문화 이야기 비율이 낮아(로그 기준 5~10%) 평균 비용 영향은 작다.
**지표** — 심사 충실성(지원되는 주장 / 전체 주장) ≥ 0.95 (현재 측정 없음). 라이브 30문항에 **장문 10문항** 추가 (S01~S10).
**위험** — 판정기가 맞는 문장을 지운다(과잉) → `partial` 은 유지, `no` 만 지움. 지운 비율을 로그로 보고 10% 넘으면 프롬프트 조정.

### G. 개인화 — 컨텍스트 밴딧으로 탐험·활용, 로그로 정책 평가

**논문** — Li, Chu, Langford & Schapire, *A Contextual-Bandit Approach to Personalized News Article Recommendation* (LinUCB, WWW 2010) · Chapelle & Li, *An Empirical Evaluation of Thompson Sampling* (NeurIPS 2011) · Dudík, Langford & Li, *Doubly Robust Policy Evaluation and Learning* (ICML 2011): **로그만으로 새 정책의 보상을 추정**(IPS/DR)해 온라인 실험 전에 거른다. 추천의 "늘 같은 것" 문제는 Covington et al., *Deep Neural Networks for YouTube Recommendations* (RecSys 2016) 가 말하는 탐험 부재다.

**푸디에 어떻게** — 음식 1만 개를 팔(arm)로 두면 표본이 모자란다. **팔 = 추천 전략**(가중치 세트), 음식은 전략이 고른다.
- 팔 6개: `open`(현재) · `taste`(취향 ×2) · `novel`(새로움 ×2) · `fame`(대표성 ×2) · `sem`(의미 ×2) · `learned`(E 의 학습 가중치). 열린 추천(`recommend`, 조건 없음)에만 적용 — 조건이 있는 질문은 조건 충족이 이끌어야 하므로 제외.
- 문맥 $x\in\mathbb{R}^{10}$: 취향 확신도 `confidence`, 탐험 나라 수 구간, 식이 조건 수, 로그인 여부, 시간대(아침·점심·저녁·야식), 입력 방식(음성·글), 최근 7일 질문 수, 열린 추천 연속 횟수("다른 거" 누른 수), 마지막 카드 탭 여부, 상수.
- **LinUCB (disjoint)**: 팔 $a$ 마다 $A_a=I_d+\sum x x^\top,\ b_a=\sum r\,x$, $\hat\theta_a=A_a^{-1}b_a$, 선택 $\arg\max_a \hat\theta_a^\top x+\alpha\sqrt{x^\top A_a^{-1}x}$, $\alpha=0.5$. 10×10 행렬 6개 — `bandit_state` 테이블 한 행(JSON)에 넣고 1분 캐시. 동률·초기엔 Thompson 으로 흔든다.
- 보상 $r\in\{0,1\}$: 같은 세션 10분 내 카드 탭·좋아요·먹어봤어요·"문화 이야기" 이어 듣기 중 하나 (events 0004). "다른 거 추천" 즉시 누름은 0.
- **propensity 기록**: 선택한 팔과 선택 확률(Thompson 샘플 비율 또는 ε)을 `conversations.strategy`, `propensity` 에. → `scripts/eval-policy.ts` 가 **IPS / DR 로 새 정책(예: 가중치 세트 바꿈)의 기대 보상을 오프라인 추정**:

  $$\hat V_{\mathrm{IPS}}(\pi)=\frac1n\sum_i \frac{\pi(a_i\mid x_i)}{\pi_0(a_i\mid x_i)}\,r_i$$

- 개인정보: 문맥에 식이 종류·종교·건강 상태는 넣지 않는다 (조건 **수**만). 11 문서 §7 과 같다.

**비용·지연** — LLM 0. 행렬 연산 µs.
**지표** — 열린 추천 1순위 다양성 90회 11종 → **25종 이상**이면서 카드 탭률 하락 없음 (인터리빙). IPS 추정과 실제 A/B 차이 ≤ 20%.
**위험** — 보상이 적어 수렴이 느리다 → 게스트는 익명 세션 단위로 집계, 팔 6개로 작게 시작. 탐험이 "대표 음식 우선 규칙"(13 문서)과 충돌 → `signatureGate` 는 모든 팔에 공통 하드 규칙.

### H. 그래프 RAG — 관계 13,464개를 "음식 로드"로

**논문** — Edge et al., *From Local to Global: A Graph RAG Approach to Query-Focused Summarization* (Microsoft, 2024): 엔티티 그래프를 **Leiden 군집**으로 나누고 군집마다 요약을 미리 써 두면 "전체를 아우르는 질문"에 강해진다. 노드 임베딩은 Grover & Leskovec, *node2vec* (KDD 2016) — 관계 구조로 "비슷한 자리"의 음식을 찾는다 (재료가 안 겹쳐도 "같은 역할"인 음식).

**푸디에 어떻게** — 배치(Python `foodis-data`) + DB
- **군집**: `food_relations`(verified) 를 무방향 가중 그래프로 (`REL_WEIGHT` 를 간선 가중치) → Leiden(`igraph`/`leidenalg`) → 군집 크기 4~40 만 채택. 예상: 만두 로드 · 커피 로드 · 쌀국수 · 납작빵 · 발효 생선 · 꼬치구이 … 수백 개.
- **군집 요약 (LLM 초안 → 사람 검수 → DB)**: 군집 음식들의 DB 문장(summary·history·origin_note)만 입력으로 "이 음식들이 어떻게 이어지는지" 300자 이야기 + 제목 + 경로(음식 순서). 결과는 **`food_roads` 테이블 (0018)** 에 `verified=false` 로 넣고 어드민이 검수 (05 문서 흐름). 검수 전에는 푸디가 쓰지 않는다 — **사실은 DB** 원칙 그대로.
- **쓰임**:
  1. `culture_story` 후보에 "로드 이야기"를 섞는다: 대상 음식이 속한 로드가 있으면 `culture_story` 대신 로드 이야기 + 다음 음식 제안 (현재의 1홉 `historical_link` 를 n홉 경로로).
  2. 새 의도 없이 **follow_up** 으로 자연스럽게: "만두 로드 따라가 볼까요?"
  3. 라디오(15 문서) 편성 단위로 재사용.
- **node2vec 임베딩** (선택, P3): 관계 그래프 128차원 → `compare_similar` 의 `similarity` 에 `graph` 신호(0.1) 추가 — 재료·태그가 안 겹쳐도 "같은 자리" (예: 각국의 '잔치 음식').

**비용** — 일회성 배치: 군집 300개 × 초안 1회 ≈ $0.3. 런타임 LLM 0 (검수된 문장을 읽을 뿐).
**지표** — 로드 이야기가 붙은 `culture_story` 답의 "이어 듣기" 비율 vs 기존 (인터리빙).
**위험** — LLM 초안이 군집 밖 사실을 보탠다 → 초안 입력에 DB 문장만, 검수 필수, F 의 주장 대조를 초안 단계에서도 돌린다.

### I. 평가 체계 — 심사·다중 턴·온라인 인터리빙

**논문** — Zheng et al., *Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena* (NeurIPS 2023): 강한 LLM 의 쌍대 비교가 사람 선호와 80%+ 일치, 단 **위치 편향**은 순서를 바꿔 두 번 물어 상쇄. Es et al., *RAGAS: Automated Evaluation of Retrieval Augmented Generation* (EACL 2024): 충실성·답 관련성·문맥 정밀도를 참조 답 없이 잰다. Chapelle et al., *Large-Scale Validation and Analysis of Interleaved Search Evaluation* (TOIS 2012): 두 순위를 **섞어 한 화면에 보여주고 클릭으로 승패**를 가리면 A/B 보다 10~100배 적은 트래픽으로 결론이 난다.

**푸디에 어떻게**
- **`pnpm eval:judge`** (`scripts/eval-judge.ts`, 프롬프트 `prompts/judge.v1.ts`) — 표본: 라이브 30 + 장문 10 + 다중 턴 60 + `conversations` 무작위 100 (개인정보 없음: 질문·후보·답만). 심사 모델은 답변 모델과 **다른 회사**(답이 Gemini 면 심사는 OpenAI/Anthropic — 자기 채점 편향 회피). 항목(0~2점):
  1. 충실성 — speech 의 주장이 후보 DB 문장에 있는가 (RAGAS faithfulness)
  2. 조건 충족 — 질문의 조건·식이·나라를 카드가 만족하는가 (규칙 결과와 교차)
  3. 이유 적절성 — `reason`·speech 의 "고른 이유"가 `matched` 와 맞는가
  4. 자연스러움·길이 — 해요체, 2~3문장, 음성으로 들을 만한가
  5. 이어가기 — follow_ups 가 막다른 길이 아닌가
  - **쌍대 모드**: v2 답 vs v3 답을 순서 바꿔 2회 → 승·무·패. 집계는 Elo 대신 단순 승률 + 95% 신뢰구간(Wilson).
- **다중 턴 세트** — `eval/dialogs.ts` 20대화 × 3턴 (지시어·비교급·배제·생략·복합·주제 전환). 오프라인(규칙 경로)은 CI, LLM 재작성 경로는 `eval:live`.
- **온라인 인터리빙** — `/api/foodi/ask` 에 `exp` 플래그: 두 랭킹(예: 현재 가중치 vs 학습 가중치)의 상위를 **팀 드래프트 인터리빙**으로 섞어 카드 순서를 만들고, 어느 팀 카드를 탭했는지 events 에 기록. 어드민 KPI(07 문서)에 승률 패널. 사용자는 차이를 못 느낀다(카드 수 같음).
- **회귀 게이트** — PR 마다: 오프라인 537+ 테스트 · `eval:retrieval` ④⑤ 하락 금지. 배포 전: `eval:live` 40문항 + `eval:judge` 충실성 ≥ 0.95.

**비용** — 심사 200문항 × 2회 × ≈ $0.001 = **$0.4/회**. 주 1회·프롬프트 변경 시.

### J. 비용·지연 — 의미 캐시 · 난이도 라우팅 · 의도 분류 증류

**논문** — Bang, *GPTCache: An Open-Source Semantic Cache for LLM Applications* (2023) · Chen, Zaharia & Zou, *FrugalGPT: How to Use Large Language Models While Reducing Cost and Improving Performance* (2023, LLM 캐스케이드) · Ong et al., *RouteLLM: Learning to Route LLMs with Preference Data* (2024) · Tunstall et al., *Efficient Few-Shot Learning Without Prompts* (SetFit, 2022) · Hsieh et al., *Distilling Step-by-Step* (ACL 2023 Findings): 큰 모델의 라벨로 작은 분류기를 만든다.

**푸디에 어떻게**
- **의미 캐시** — `lib/guard/semantic-cache.ts`. 이미 병렬로 계산하는 질의 임베딩을 쓴다. `response_cache` 에 `embedding vector(1536)` · `spec_hash` · `profile_key` 열 추가 (0017), 조회는 `match_cache(embedding, profile_key, spec_hash)` RPC(HNSW). 적중 조건: 코사인 ≥ **0.95** ∧ `QuerySpec` 해시 일치(부정·재료·식이가 같아야 — "안 매운"과 "매운"은 임베딩이 가깝다) ∧ 프로필 키(식이·알레르기·탐험 구간·DNA 상위 3·모델) 일치 ∧ history 없음. 적중 답은 `cached: true, cache: "semantic"` 으로 표시.
- **난이도 라우팅** — 사용자 선택('푸디의 두뇌')이 없을 때만. 규칙: 의도 `recommend`·`filter_by_diet` 이고 D 판정 "확실" → **fast 티어**로 생성(지금은 `smart`; 둘 다 Flash-Lite 라 지금은 동일하지만 모델을 올릴 때 비용을 가른다). `culture_story`·`explain_food`·D "애매" → smart. 캐스케이드: fast 답이 규칙 검증에 실패하면 재시도는 smart 로 (FrugalGPT).
- **의도 분류 증류** — `conversations` 에서 `via="llm"` 턴의 (질문, LLM 의도·슬롯) 1,000건 이상 쌓이면: ① 자주 나온 표현을 `vocab.ts` 상황표·규칙에 보탠다(반자동: 빈도표 스크립트) ② **임베딩 kNN 분류기** — 라벨된 질문 임베딩을 `intent_examples` 테이블에, 새 질문은 임베딩이 어차피 있으니 k=7 이웃 다수결(코사인 ≥ 0.85 일 때만 채택). SetFit 의 "임베딩 + 작은 머리" 를 학습 없이 흉내 낸 것. LLM 의도 호출 비율 50% → **20% 이하** 목표.

**비용·지연** — 의미 캐시 적중 시 LLM 0·지연 ≈ 임베딩 1회(0.3초). 라우팅은 0. kNN 은 DB 1회(HNSW, ms).
**지표** — 캐시 적중률(정확+의미) +20%p, 질문당 평균 비용, 의도 LLM 호출 비율.
**위험** — 의미 캐시 오적중("태국 음식" ↔ "타이 음식"은 OK, "태국" ↔ "대만"은 안 됨) → 나라 코드도 `spec_hash` 에 포함, 임계 0.95 부터 보수적으로, 오적중 신고 버튼(👎)을 캐시 무효화에 연결.

### K. 사회적 대화 층 — "안녕 푸디야" → "안녕하세요, 사용자님!" ★ 이 PR 에서 구현

**논문** — Zhang et al., *Personalizing Dialogue Agents: I have a dog, do you have pets too?* (Persona-Chat, ACL 2018): 일관된 **페르소나 문장**을 가진 대화 모델이 잡담에서 더 매력적이고 일관되다. Roller et al., *Recipes for Building an Open-Domain Chatbot* (BlenderBot, EACL 2021): 좋은 잡담의 핵심은 **인격 · 공감 · 지식의 혼합**과 "대화를 이어가는 질문". Stolcke et al., *Dialogue Act Modeling* (Computational Linguistics 2000): 발화를 **대화 행위**(인사·감사·작별·질문 …)로 먼저 분류하면 응답 전략이 단순해진다. 음성 비서 설계 관행(Google Conversation Design: "acknowledge, then move forward")도 같은 말을 한다 — **받아 주고, 앞으로 이끈다.**

**지금까지의 문제** — "안녕 푸디야"는 규칙이 못 잡아 LLM 으로 가고(비용·0.5초), LLM 은 `out_of_scope` 로 분류해 "그 이야기는 제가 잘 몰라요"라고 답했다. 인사를 거절하는 안내자였다.

**푸디에 어떻게** — `lib/foodi/social.ts` (구현됨)
- **대화 행위 9종**을 규칙으로: `greet`(안녕·하이·오랜만) · `how_are_you`(잘 지냈어·밥 먹었어) · `thanks` · `compliment`(최고야·똑똑하네) · `bye`(잘가·잘자) · `who`(넌 누구야) · `can`(뭐 할 수 있어) · `mood`(심심해·우울해·피곤해) · `chat`(LLM 이 social 로만 분류한 그 밖의 잡담).
- **발화 전체가 사회적 표현일 때만** 잡는다 (`socialKey`: 호출어·문장부호·끝의 '요'를 뗀 뼈대를 앵커 정규식과 대조). "안녕 푸디야, 오늘 뭐 먹지?"는 인사가 아니라 추천 — 음식 질문이 늘 이긴다. "배고파"·"출출해"는 social 이 아니라 **추천 요청**으로 (RECOMMEND 규칙에 추가).
- **답은 LLM 없이** 페르소나 문장 + DB 값: 호칭(`profiles.display_name` → "{이름}님", 없으면 "사용자님"), 한국 시간대 인사(아침·점심·저녁·밤), 탐험 나라 수("4개 나라를 탐험하셨네요"), 지도 나라 수(`countries` 테이블). 문장 변형은 **같은 날·같은 사람은 같은 문장**(씨앗 해시) — 음성 답이 흔들리지 않으면서 날마다 조금씩 다르다.
- **늘 앞으로 이끈다** — 모든 답의 마지막은 탐험 제안("오늘은 어느 나라로 떠나볼까요?") + follow_ups (탐험 기록이 있으면 "안 가본 나라 음식 추천").
- 파이프라인: `ruleClassify` 맨 앞에서 `detectSocial` → `intent: "social"` → 오케스트레이터는 **의도 LLM·임베딩·검색을 전부 건너뛰고** `socialAnswer`. 캐시하지 않는다(이름·시간이 들어간다). 의도 분류 프롬프트에도 `social` 을 추가해 규칙이 놓친 잡담("오늘 기분 어때?")을 LLM 이 `social` 로 보내면 `chat` 문장으로 받는다.
- 개인정보: 이름은 호칭에만 쓰고 **LLM 프롬프트에는 넣지 않는다**(UserContext.displayName 은 generate 의 profile 에 포함되지 않음).

**비용·지연** — 0 (규칙 + 템플릿). 인사 한 번에 LLM 2회(의도·답)를 부르던 것이 0회가 됐다.
**지표** — 평가 문항 G01~G03 추가 (`eval/cases.ts`: 인사 → social·호칭·카드 0, 감사, 인사+질문 → recommend). `social.test.ts` 25건: 9종 감지·음식 질문 비감지·호칭·시간대·결정적 변형·오케스트레이터 무호출.
**다음** — ① 대화 상태(A)가 생기면 "아까 그 태국 음식 어땠어요?" 같은 **재방문 인사**(마지막 대화의 카드를 DB 에서) ② 어드민에서 페르소나 문장 편집 ③ 로그의 `out_of_scope` 발화를 모아 사회적 표현 사전 확장(J-증류와 같은 흐름).

P1 은 전부 `pnpm test` 로 검증되는 순수 함수 + 1개 마이그레이션이라 먼저 간다. 발표(경진대회) 전이라면 **P1 + F(검증 사슬)** 까지가 "보여줄 수 있고 안전한" 선이다.

## 8. 위험과 대응

| 위험 | 대응 |
|---|---|
| 새 LLM 호출이 사실을 만든다 (재작성·계획·HyDE·요약) | 출력은 전부 "DB 안의 것 고르기 / 지우기 / 검색 열쇠"로 제한. 이름 인식기로 **질문·history 에 없는 음식 이름이 나오면 폐기**. 로드 이야기는 검수 전 미사용 |
| 지연이 늘어 음성 UX 가 깨진다 | 단순 질문 경로는 추가 호출 0. 추가 호출은 전부 "애매·장문·복합·지시어" 조건부. 각 호출에 abort 예산(재작성 1.5초 · 재정렬 2초 · 검증 2초) — 넘기면 v2 결과 사용 |
| 비용 | 질문당 상한 모니터(api_usage, 60초 캐시 집계). `overBudget` 이면 v3 층 전부 끔 |
| 주입 (history·재작성 경유) | history 는 `<history>` 데이터 블록, 프롬프트 규칙 10 유지. 재작성 출력에 지시문(규칙 무시·시스템·프롬프트)이 들면 폐기 |
| 캐시 오적중 | 임계 0.95 + spec_hash + 나라 코드 + 👎 무효화 |
| 밴딧이 소수 사용자에 과적합 | 팔 6개·문맥 10차원으로 작게. 게스트는 세션 단위. `signatureGate` 공통 |
| 평가 심사의 편향 | 다른 회사 모델로 심사, 순서 바꿔 2회, 사람 표본 30문항과 일치율 ≥ 80% 확인 후 신뢰 |
| 회귀 | 플래그 전부 끄면 v2 와 동일. 537 테스트 + 30문항 + `eval:retrieval` ④⑤ 가 PR 게이트 |
