# 🏆 06 경진대회 전략 · 발표 구성

> 🏆 발표의 구조는 **문제 → 해결 → 경험(데모) → 기술 → 증명** 순서. 데모를 가운데 둔다. 기술 설명은 데모에서 본 것을 "어떻게 동작했나"로 풀어야 심사위원이 따라온다.

## 1. 평가 기준 매핑

| 기준 (배점) | 심사위원이 보는 것 | FOODIS의 답 | 발표에서 보여줄 증거 |
|---|---|---|---|
| 아이디어·문제 정의 (30) | 문제가 진짜인가, 참신한가, 쓸모 있는가 | "음식 검색은 많지만 음식으로 세계 탐험은 없다" + 식이 조건 사용자의 실제 고통 | 경쟁 서비스 비교표 1장, 비건 시나리오 데모 |
| 기술 구현 수준 (30) | 기술이 적절한가, 설계가 있는가, 어려운 걸 했는가 | 자체 DB + RAG + 검증 레이어 + 음성 파이프라인 + 역이용 개인화 | 아키텍처 1장, RAG 8단계 1장, "할루시네이션 방지 5감의 방어" 1장 |
| 완성도 (20) | 실제로 돌아가나, 안 뮤추나 | 핵심 루프 라이브 데모 + 오인식 복구 UX | 라이브 3분 + 백업 영상. 데모 도중 "심사위원님이 직접 질문해 보세요" 제안(자신감) |
| 발표·설명 (20) | 구성, 기술 설명, Q&A, 역할, AI/라이브러리 사용 설명 | 역할별 발화자 전환, "우리가 만든 것 / API로 가져온 것" 명시 | 기술 구성도에 범레(자체 구축 vs 외부 API) 색 구분 |

## 2. 핵심 차별점 5개 (발표에서 반복할 문장)

1. **검색창이 없다. 푸디에게 묻는다.** — Voice First를 1순위 인터페이스로 쌌 음식 문화 서비스.
2. **AI가 음식을 발명하지 않는다.** — 자체 검수 DB가 후보를 고르고, AI는 설명하고, 서버가 검증한다.
3. **식이 조건은 필터가 아니라 정직이다.** — ✅⚠️❓ 3단계, 모르면 모른다고 말하는 AI.
4. **음식은 검색 결과가 아니라 노드다.** — 관계 데이터로 한국 만두에서 폴란드 피에로기로 이어지는 탐험.
5. **쓸수록 달라지는 서비스.** — Passport·Food DNA가 다음 추천의 입력이 되는 역이용 구조.

## 3. 발표 구성 (12분 + Q&A)

| 시간 | 섹션 | 내용 | 슬라이드 |
|---|---|---|---|
| 0:00~0:40 | 오프닝 | 인트로 연출(국기→FOOD) 영상으로 시작. "Different Cultures, One Table." 발표자가 첫 질문을 던진다: "여러분은 몇 개 나라의 음식을 먹어봤나요?" | 1 |
| 0:40~2:30 | 문제 | 문제 5가지를 2개로 압축: ① 음식으로 세계를 탐험할 곳이 없다 ② 식이 조건 사용자는 매번 확인해야 한다. 경쟁 비교표. | 2~3 |
| 2:30~3:30 | 해결 | 한 줄 정의 + 4기둥(Explore/Discover/Personalize/Connect). "검색하지 않아도 된다." | 4 |
| 3:30~6:30 | **라이브 데모** | 시나리오 A(추천→상세→연결→Passport) 2분 + 시나리오 B(비건 인도 음식, ⚠️ 배지) 1분. 마지막에 DB에 없는 질문으로 "모른다고 말하는 AI" 보여주기. | 앱 |
| 6:30~9:00 | 기술 | 아키텍처 → "방금 본 답변이 어떻게 나왔나" RAG 8단계를 데모 질문 하나로 역일 → 할루시네이션 5감 방어 → DB 스키마·지식 그래프 시각화(만두 로드). 자체 구축 vs API 색 구분. | 5~8 |
| 9:00~10:00 | 데이터·신뢰성 | 30국가 × N음식, 검수 프로세스, 출처 관리. "이 데이터가 우리의 기술 난이도입니다." | 9 |
| 10:00~11:00 | 역할·AI 사용 설명 | 팀원별 맡은 부분. 사용한 AI/라이브러리 목록과 그 위에 우리가 발은 것(스키마, 검증, 데이터, UX). | 10 |
| 11:00~12:00 | 확장·마무리 | 로드맵(Map, Radio, Image, Journey, World Table). 마무리: "푸디야, 오늘은 어디로 떠나볼까?" — 심사위원에게 직접 마이크 건내기 제안. | 11~12 |

## 4. 예상 Q&A

| 질문 | 답변 걸자 |
|---|---|
| ChatGPT에 물어보는 것과 뭔가 다릅니까? | 세 가지. ① 답이 검수된 DB에서 나오고 검증된다(식이 정보) ② 음식 간 관계로 탐험이 이어진다(막다른 답 없음) ③ 내 탐험 기록이 다음 추천을 바꾼다. ChatGPT는 세션이 끝나면 잊는다. |
| AI가 틀린 할랄 정보를 주면 어떻게 합니까? | AI는 할랄 여부를 말할 수 없다. 배지는 DB 커럼에서 서버가 그린다. DB는 2개 출처 일치 시에만 yes/no, 아니면 '확인 필요'. |
| 데이터 200개는 적지 않나요? | 맞다. 그래서 MVP는 '넓게'가 아니라 '깊게 연결된' 200개다. 관계 300건이 핵심. 입력 파이프라인(LLM 초안→검수)이 있어 확장은 사람 시간에만 비례한다. |
| 음성 인식이 안 되면? | 인식 텍스트를 화면에 보여주고 탭해서 수정, 텍스트 입력도 가능. Web Speech 실패 시 Whisper fallback. |
| 왜 지도가 없나요? | 핵심 루프(음성→추천→탐험→기록)에 직접 기여하지 않아 의도적으로 버렸다. 기능 수보다 루프 완성도. 확장 1순위. |
| 수익 모델은? | 관광청·식품 브랜드와 국가 콘텐츠 파트너십, 식이 조건 사용자 대상 프리미엄(식당 연동). 단, 경진대회 범위 밖. |
| 사용자 데이터(식이 조건)는 민감하지 않나요? | 식이 프로필은 기기·계정 내 추천 필터로만 사용, 종교·건강 추론 금지, 삭제 가능. Supabase RLS로 본인만 접근. |

## 5. 역할 분담 (예시 — 팀 구성에 맞게 수정)

| 역할 | 책임 | 발표 담당 섹션 |
|---|---|---|
| 기획·PM | 문제 정의, MVP 경계, 시나리오, 발표 구성 | 오프닝·문제·해결·마무리 |
| AI·백엔드 | RAG, 프롬프트, 검증, STT/TTS 파이프라인 | 기술 섹션 |
| 데이터 | 스키마, 데이터 입력·검수, 관계, 출처 | 데이터·신뢰성 섹션 |
| 프론트·디자인 | PWA, 인트로 연출, 컴포넌트, 데모 안정성 | 라이브 데모 |

## 6. 데모 리스크 대비

- 현장 네트워크: 핫스팟 준비 + 데모 10개 질문의 응답 캐시(응답 해시 기반) + 백업 영상.
- 마이크 소음: 텍스트 입력 전환 버튼 항시 노출. 연습 시 스피커로 TTS 음량 확인.
- LLM 지연: 첫 문장 우선 TTS + "푸디가 지도를 보고 있어요" 상태 애니미이션으로 3초는 자연스럽게 보이게.
- 리허설 3회 이상, 각 회차 계산 시간 12분 이내 확인.
